## 1. SonarQube Basics

### Q1. What is SonarQube?

SonarQube is a code quality and security analysis platform. It performs static analysis to identify bugs, vulnerabilities, code smells, and maintainability issues without executing the application.

Common capabilities include:

- Detecting potential bugs and security issues.
- Identifying maintainability problems and code duplication.
- Importing code coverage reports generated by test tools.
- Enforcing standards through Quality Gates.
- Integrating with CI/CD tools such as Jenkins, GitLab CI/CD, and Azure DevOps.

### Q2. Why is SonarQube used in DevOps?

SonarQube automates code quality checks in the CI/CD pipeline. A typical pipeline checks out the code, builds the application, runs tests, performs analysis, and evaluates the Quality Gate before allowing later stages to proceed.

Benefits include earlier detection of defects, more consistent coding standards, better visibility into technical debt, and automated quality controls.

### Q3. What is static code analysis?

Static analysis examines source code without running the application. SonarQube applies language-specific rules to identify likely defects, security weaknesses, and maintainability issues.

Static analysis complements unit testing, integration testing, and dynamic security testing; it does not replace them.

### Q4. Explain the main components of SonarQube architecture.

- **SonarQube Server:** Hosts the application, project settings, and analysis results.
- **Database:** Stores persistent configuration and analysis data according to the deployment architecture.
- **Scanner:** Runs in the build environment, analyzes source code, and submits a report.
- **Compute Engine:** Processes submitted reports and updates analysis results.
- **Web interface:** Displays issues, metrics, and Quality Gate status.
- **Language analyzers/plugins:** Provide analysis rules and language support.

Typical flow:

`Developer → Git → CI/CD pipeline → Scanner → SonarQube Server → Compute Engine → Quality Gate result`

Exact architecture depends on the SonarQube version and deployment model.

### Q5. What is SonarScanner?

SonarScanner is the tool that performs analysis and submits the report to SonarQube. It can be used through the CLI or through build integrations such as Maven and Gradle.

Example:

```bash
sonar-scanner \
  -Dsonar.projectKey=my-app \
  -Dsonar.sources=src \
  -Dsonar.host.url=https://sonarqube.example.com
```

Configure authentication securely through CI/CD credentials or another secrets manager. Do not hardcode tokens in source control.

## 2. Important Concepts

### Q6. What is a Quality Gate?

A Quality Gate is a set of conditions that determines whether an analysis meets the project's quality requirements.

Example conditions might include:

- New-code coverage of at least 80%.
- No new blocker issues.
- New-code duplication below a defined threshold.

These are examples, not universal defaults. The actual conditions depend on project configuration and SonarQube version.

- **Passed:** All configured conditions are satisfied.
- **Failed:** At least one configured condition is not satisfied.

A CI/CD pipeline can be configured to stop when the Quality Gate fails.

### Q7. What is a Quality Profile?

A Quality Profile is a collection of analysis rules for a programming language. It determines which rules are used to identify issues.

Examples include rules for unused variables, possible null pointer errors, complex methods, and unsafe coding practices.

**Remember:** Quality Profile = rules applied during analysis. Quality Gate = conditions for passing or failing an analysis.

### Q8. What is the difference between a bug, vulnerability, and code smell?

- **Bug:** A potential defect that can cause incorrect behavior, such as a possible null dereference.
- **Vulnerability:** A potential security weakness, such as unsafe construction of a SQL query.
- **Code smell:** A maintainability issue, such as duplicated logic or an overly complex method.

A code smell is not necessarily a functional defect or an exploitable security issue.

### Q9. What is the difference between new code and overall code?

- **New code:** Code covered by the project's configured new-code definition.
- **Overall code:** The broader codebase included in the analysis.

Teams often focus Quality Gate conditions on new code so they can prevent new problems without immediately fixing every historical issue.

For example, overall coverage might be 55%, while new-code coverage is 85%. If the configured gate requires 80% coverage on new code, the coverage condition can pass.

### Q10. What is technical debt?

Technical debt is an estimate of the effort needed to remediate maintainability issues identified by analysis. Examples include duplicated code and overly complex methods.

Reducing technical debt can make the application easier to maintain and extend.

### Q11. What is the difference between code coverage and duplication?

- **Code coverage:** Measures how much code is exercised by tests, based on coverage reports imported into SonarQube.
- **Code duplication:** Measures duplicated code detected by the analyzer.

High coverage does not guarantee that code is secure or defect-free.

### Q12. Does SonarQube execute unit tests?

No. Unit tests are executed by tools such as JUnit, Maven Surefire, or Gradle. Coverage tools such as JaCoCo generate reports that SonarQube can import.

A typical sequence is:

1. Compile the application.
2. Run unit tests.
3. Generate coverage reports.
4. Run SonarQube analysis.
5. Evaluate the Quality Gate.

## 3. Jenkins Integration

### Q13. How do you integrate SonarQube with Jenkins?

1. Install and configure SonarQube.
2. Generate an appropriate SonarQube token.
3. Configure the SonarQube server in Jenkins.
4. Store the token securely in Jenkins Credentials.
5. Configure SonarScanner or the relevant build-tool integration.
6. Add analysis to the pipeline.
7. Wait for the Quality Gate result.
8. Fail the pipeline if the gate fails, when required by policy.

The SonarQube Scanner for Jenkins plugin provides integration with the SonarQube server and pipeline steps.

### Q14. Show a Jenkins pipeline for SonarQube analysis.

This example uses Maven for a Java application:

```groovy
pipeline {
    agent any

    tools {
        jdk 'JDK17'
        maven 'Maven3'
    }

    stages {
        stage('Checkout') {
            steps {
                git branch: 'main',
                    url: 'https://github.com/example/my-app.git'
            }
        }

        stage('Build and Test') {
            steps {
                sh 'mvn clean verify'
            }
        }

        stage('SonarQube Analysis') {
            steps {
                withSonarQubeEnv('SonarQube-Server') {
                    sh 'mvn sonar:sonar -Dsonar.projectKey=my-app'
                }
            }
        }

        stage('Quality Gate') {
            steps {
                timeout(time: 10, unit: 'MINUTES') {
                    script {
                        def qg = waitForQualityGate()
                        if (qg.status != 'OK') {
                            error "Quality Gate failed: ${qg.status}"
                        }
                    }
                }
            }
        }
    }
}
```

**Configuration notes:**

- `JDK17` and `Maven3` must be configured in Jenkins.
- `SonarQube-Server` must match the configured server name.
- Install the Jenkins SonarQube plugin and configure authentication.
- Configure the SonarQube webhook to point to Jenkins, commonly `https://jenkins.example.com/sonarqube-webhook/`.
- Replace the example repository URL and project key.
- This pipeline assumes the Maven project is configured for SonarQube analysis.

### Q15. What does `withSonarQubeEnv()` do?

It is a pipeline step provided by the SonarQube Scanner for Jenkins plugin. It sets up the environment for communicating with the configured SonarQube server.

```groovy
withSonarQubeEnv('SonarQube-Server') {
    sh 'mvn sonar:sonar'
}
```

The server name must match the Jenkins configuration.

### Q16. What does `waitForQualityGate()` do?

It waits for the Quality Gate result of a submitted SonarQube analysis. It is often used to prevent deployment when the configured quality conditions fail.

```groovy
timeout(time: 10, unit: 'MINUTES') {
    def qg = waitForQualityGate()
    if (qg.status != 'OK') {
        error 'SonarQube Quality Gate failed'
    }
}
```

A configured and reachable SonarQube webhook is normally required for the Jenkins integration to receive the result. This step waits for the result; it does not run the scan itself.

### Q17. How do you configure SonarScanner CLI in Jenkins?

Configure the scanner on the Jenkins agent or through Jenkins tool configuration, then run it inside `withSonarQubeEnv()`.

```groovy
stage('Code Analysis') {
    steps {
        withSonarQubeEnv('SonarQube-Server') {
            sh '''
                sonar-scanner \
                  -Dsonar.projectKey=my-app \
                  -Dsonar.sources=src
            '''
        }
    }
}
```

The source path and scanner installation must match the project and build agent.

### Q18. How do you pass the SonarQube token securely?

Store the token in Jenkins Credentials rather than hardcoding it in the Jenkinsfile or committing it to Git.

Example using a Jenkins secret-text credential:

```groovy
withCredentials([
    string(
        credentialsId: 'sonarqube-token',
        variable: 'SONAR_TOKEN'
    )
]) {
    sh '''
        sonar-scanner \
          -Dsonar.projectKey=my-app \
          -Dsonar.token="$SONAR_TOKEN"
    '''
}
```

Use least-privilege credentials, rotate them when appropriate, and avoid printing secrets in logs. The credential ID must exist in Jenkins.

## 4. Coverage and Analysis Configuration

### Q19. How do you configure code coverage for Java?

Use a coverage tool such as JaCoCo to generate a report, then configure SonarQube to import it.

Example, assuming the Maven build generates the XML report at the shown path:

```bash
mvn clean verify sonar:sonar \
  -Dsonar.projectKey=my-app \
  -Dsonar.coverage.jacoco.xmlReportPaths=target/site/jacoco/jacoco.xml
```

The JaCoCo plugin must be configured in the project, and the report must exist before analysis.

### Q20. Why does SonarQube show 0% coverage?

Common causes:

1. Tests were not executed.
2. The coverage report was not generated.
3. The report path is incorrect.
4. The report is in an unsupported format.
5. The report was generated in a different workspace.
6. Analysis ran before report generation.
7. Report data does not match the analyzed source files.

**Troubleshooting checklist:**

- Inspect Jenkins console output.
- Confirm tests actually ran.
- Verify that the XML report exists and contains coverage data.
- Check the configured report path.
- Review scanner logs.
- Confirm that the report corresponds to the current source code.

### Q21. How do you exclude files from analysis?

Use `sonar.exclusions` to exclude matching files from the relevant analysis scope.

```properties
sonar.exclusions=**/generated/**,**/vendor/**
```

To exclude files from coverage calculations while retaining them in code analysis:

```properties
sonar.coverage.exclusions=**/generated/**,**/*Config.java
```

Analysis exclusions and coverage exclusions are different. Avoid excluding important application code without a valid reason.

### Q22. What is the difference between `sonar.sources` and `sonar.tests`?

- `sonar.sources` identifies source-code files for analysis.
- `sonar.tests` identifies test-code files.

Example:

```properties
sonar.sources=src/main/java
sonar.tests=src/test/java
```

Maven analysis often detects a standard project layout automatically, but these properties can be useful for explicit configuration.

### Q23. What is a project key?

The project key uniquely identifies a project in SonarQube and associates its analysis results with that project.

```properties
sonar.projectKey=payment-service
```

Keep the key consistent across pipeline runs for the same project.

### Q24. What is a SonarQube token?

A token is an authentication credential used by CI/CD tools and other clients. Its permitted actions depend on its type and permissions.

Best practices:

- Store it in Jenkins Credentials or a secrets manager.
- Grant only required permissions.
- Do not commit it to source control.
- Rotate or revoke it when needed.

## 5. Scenario-Based Questions

### Q25. Jenkins fails because the Quality Gate failed. What do you do?

1. Identify the failed Jenkins stage.
2. Open the SonarQube project dashboard.
3. Inspect the failed Quality Gate conditions.
4. Identify whether the failure relates to coverage, bugs, vulnerabilities, duplication, or another configured condition.
5. Review the affected code with developers.
6. Fix the underlying issue and rerun tests and analysis.

Do not disable the gate merely to make the pipeline pass. Use the approved exception process if a genuine exception is necessary.

### Q26. The analysis succeeds, but Jenkins waits indefinitely for the Quality Gate. How do you troubleshoot it?

- Verify that the analysis report was submitted successfully.
- Check the SonarQube webhook configuration and delivery logs.
- Confirm the webhook points to the correct Jenkins endpoint.
- Verify Jenkins is reachable from the SonarQube server.
- Review Jenkins and SonarQube logs.
- Confirm the Jenkins plugin and server configuration are correct.
- Check that the pipeline is waiting for the expected analysis.

A common cause is an incorrect or unreachable webhook URL. The usual endpoint is:

```text
https://jenkins.example.com/sonarqube-webhook/
```

Use the actual Jenkins URL and endpoint for your environment.

### Q27. SonarQube analysis fails with an authentication error. What do you check?

- Token validity, expiration, or revocation.
- Whether the correct Jenkins credential is being used.
- Whether the token is passed correctly to the scanner.
- Whether the token has sufficient permissions.
- Whether the server URL is correct.

Update the credential securely if necessary. Do not expose the token in logs.

### Q28. SonarQube is down. What happens to the pipeline?

It depends on the pipeline design. If quality analysis is mandatory, the pipeline should normally fail when analysis cannot complete. If the organization allows temporary exceptions, follow the documented incident or exception process.

Troubleshooting steps include checking service/container health, application logs, database connectivity, disk space, memory, and connectivity from Jenkins agents.

### Q29. The SonarQube server is slow. How do you troubleshoot it?

1. Check CPU and memory usage.
2. Inspect application and Compute Engine logs.
3. Check for a backlog of analysis reports.
4. Verify database connectivity and performance.
5. Check disk usage and storage.
6. Look for large projects or excessive concurrent analyses.
7. Review recent infrastructure or configuration changes.

Address the identified bottleneck through resource tuning, concurrency changes, analysis-scope improvements, or database investigation as appropriate.

### Q30. Code passed yesterday but fails today. Why?

Possible causes include:

- New issues introduced in the latest code.
- Quality Gate conditions changed.
- Quality Profile rules changed.
- New-code definition changed.
- SonarQube version or analyzer rules changed.
- Coverage report changed or was missing.
- Analysis scope changed.

Compare the two analyses, inspect the current Quality Gate conditions, and review recent configuration and code changes.

### Q31. How do you prevent merging code that fails SonarQube?

1. Trigger CI on pull requests.
2. Build the application and run tests.
3. Run SonarQube analysis.
4. Publish the Quality Gate result.
5. Configure the source-control platform to require the relevant successful status check before merging.

The exact setup depends on the source-control platform, integration, and SonarQube edition. A dashboard result alone does not block a merge; branch protection or equivalent merge enforcement must be configured.

### Q32. How do you integrate SonarQube with GitLab CI/CD?

Configure the SonarQube URL and token as GitLab CI/CD variables, then add an analysis job. Example:

```yaml
stages:
  - build
  - test
  - quality

sonarqube-check:
  stage: quality
  image: maven:3-eclipse-temurin-17
  variables:
    SONAR_USER_HOME: "${CI_PROJECT_DIR}/.sonar"
  cache:
    key: "${CI_JOB_NAME}"
    paths:
      - .sonar/cache
  script:
    - mvn verify sonar:sonar
        -Dsonar.projectKey=my-app
        -Dsonar.host.url="$SONAR_HOST_URL"
        -Dsonar.token="$SONAR_TOKEN"
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
    - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'
```

This is a simplified example. Configure `SONAR_HOST_URL` and `SONAR_TOKEN` as CI/CD variables, protect sensitive values, and adjust the image and Maven setup to the project.

For production use, ensure the pipeline explicitly enforces the Quality Gate before merge or deployment. The exact implementation depends on your SonarQube edition and GitLab integration.

### Q33. How do you integrate SonarQube into a Docker-based pipeline?

A typical flow is:

1. Check out source code.
2. Build the application in a container.
3. Run tests and generate coverage reports.
4. Run SonarQube analysis from the CI environment or a dedicated build container.
5. Evaluate the Quality Gate.
6. Build and publish the Docker image if required checks pass.
7. Deploy the approved image.

Ensure the scanner can access the source, build outputs, coverage reports, and SonarQube server. Supply tokens through CI/CD secrets; never bake them into the image.

### Q34. How do you upgrade SonarQube in production?

1. Review the official upgrade documentation and supported upgrade path.
2. Check database, Java/runtime, and plugin compatibility as applicable to the version.
3. Back up the database and relevant configuration.
4. Test the upgrade in staging.
5. Schedule maintenance if required.
6. Upgrade according to the documented procedure.
7. Validate server health, project access, and analysis.
8. Monitor logs and pipeline behavior.

Do not upgrade production without a verified backup and recovery plan.

### Q35. What is the difference between SonarQube and SonarQube Cloud?

SonarQube Server is self-managed by the organization, while SonarQube Cloud is a cloud-based service managed by the provider.

| Area | SonarQube Server | SonarQube Cloud |
|---|---|---|
| Hosting | Organization-managed | Provider-hosted |
| Infrastructure maintenance | Primarily the organization's responsibility | Primarily provider-managed |
| Infrastructure control | Greater control | Less direct control |
| CI/CD integration | Supported | Supported |

Feature availability, pricing, and integrations depend on the current offering and plan.

## 6. Advanced Questions

### Q36. What is pull request analysis?

Pull request analysis evaluates proposed code changes before they are merged. It can identify issues in new code and report analysis status in the pull request workflow, depending on the SonarQube edition and source-control integration.

This helps teams catch problems early and avoid adding technical debt.

### Q37. Do all SonarQube editions support the same features?

No. Feature availability varies by distribution, edition, and version. Branch analysis, pull request analysis, governance, and other capabilities may have edition-specific requirements.

Check the current official documentation and licensing before designing a pipeline around a specific feature.

### Q38. What is a Security Hotspot?

A Security Hotspot is a location in code that uses a security-sensitive practice and requires review. It is not automatically a confirmed vulnerability.

For example, code involving file access, cryptographic operations, or security-sensitive configuration may need review.

- **Vulnerability:** A potential security defect identified by analysis.
- **Security Hotspot:** Code requiring review to determine whether the practice is safe in context.

### Q39. How do you handle false positives?

1. Review the reported issue and the relevant code.
2. Validate whether the issue is genuinely present.
3. Consult the development or security team if needed.
4. Mark it as a false positive only when evidence supports that conclusion and the workflow permits it.
5. Document the reasoning where appropriate.

Avoid disabling rules broadly just to reduce the issue count.

### Q40. Which SonarQube metrics do you monitor as a DevOps Engineer?

| Metric | Why it matters |
|---|---|
| Quality Gate status | Shows whether configured quality conditions pass |
| New-code coverage | Measures test coverage for new code |
| Bugs | Highlights potential functional defects |
| Vulnerabilities | Highlights potential security weaknesses |
| Security Hotspots | Tracks code requiring security review |
| Code smells | Identifies maintainability issues |
| Duplicated lines | Measures duplicated code |
| Technical debt | Estimates maintainability remediation effort |
| Analysis duration | Helps identify slow CI jobs |
| Compute Engine processing | Helps identify server-side analysis backlogs |

Focus on new-code quality, pipeline reliability, and analysis duration rather than treating one metric as a complete measure of software quality.

## 7. Useful Commands

### Run SonarQube analysis with Maven

```bash
mvn clean verify sonar:sonar \
  -Dsonar.projectKey=my-app \
  -Dsonar.host.url=https://sonarqube.example.com \
  -Dsonar.token="$SONAR_TOKEN"
```

The Maven project and SonarQube analysis configuration must be set up correctly.

### Run SonarScanner CLI

```bash
sonar-scanner \
  -Dsonar.projectKey=my-app \
  -Dsonar.sources=src \
  -Dsonar.host.url=https://sonarqube.example.com \
  -Dsonar.token="$SONAR_TOKEN"
```

### Check whether the server endpoint is reachable

```bash
curl -sS -o /dev/null -w "%{http_code}\n" \
  https://sonarqube.example.com/api/system/status
```

This checks the HTTP response. It does not by itself confirm that every SonarQube subsystem is healthy.

### Check SonarQube container logs

```bash
docker logs sonarqube --tail 100
```

Use this when the container is named `sonarqube`.

### Check container status

```bash
docker ps -a
```

### Check Linux disk space

```bash
df -h
```

### Check Linux memory

```bash
free -h
```

**Security reminder:** Avoid putting real tokens into shell commands that may be stored in shell history or exposed through process inspection. Prefer secure credential injection from your CI/CD system.

## 9. Sample Interview Answer

**Question: Explain your SonarQube experience.**

Adapt this answer to match your real work experience:

> In my DevOps workflow, SonarQube is integrated into the CI/CD pipeline to maintain code quality and identify potential security issues before deployment.
>
> I configure the SonarQube integration with Jenkins, manage authentication tokens through Jenkins Credentials, and add an analysis stage to the pipeline.
>
> For Java applications, I use Maven to build the application and execute unit tests. When coverage is required, I configure JaCoCo to generate the report and make it available to SonarQube.
>
> After analysis, I check the Quality Gate status. If the gate fails, I review the failed conditions, such as insufficient coverage or newly introduced issues, and work with the development team to resolve them.
>
> I also troubleshoot common problems such as authentication failures, missing coverage reports, webhook connectivity issues, and slow analysis.
>
> My objective is to automate code quality checks and ensure that applications meet the team's quality requirements before they proceed to deployment.

**Interview tip:** If asked about a production incident, describe one you genuinely handled. Do not present a hypothetical situation as personal experience.
